# 步骤 2 至步骤 4 实现说明

> 本文保留原始 2D5P/3D7P 与 LLVM 18 开发记录。迁移分支当前实现以
> `stencil_all_sme.cpp` 的 kernel-only IR 为输入，支持 1D3P、2D5P/9P、
> 3D7P/13P/25P/27P；实际构建和输出路径以本目录 `README.md` 为准。

本文根据 `02_llvm_pass_plugin` 中的实际代码，说明 LLVM pass 插件建立、
stencil 识别、预取决策和安全地址插入分别完成了什么。方案原理见仓库根目录
的 `stencil预取优化实施方案.md`，构建命令见本目录的 `README.md`。

## 1. 整体执行流程

插件处理一份由原始 SME/SVE ACLE C kernel 生成的 LLVM IR：

```text
Clang 生成 LLVM IR
  -> StencilPrefetchPass 获取 LLVM analyses
  -> analyzeStencilFunction 识别 stencil 和物理流
  -> decidePrefetches 为每条物理流生成并筛选候选
  -> insertPrefetches 构造受保护的未来地址
  -> 插入 llvm.aarch64.prefetch
  -> AArch64 后端生成 PRFM/PRFUM
```

分析、决策和插入发生在同一次 function pass 运行中。中间结果只保存在
`StencilInfo`、`StreamInfo` 和 `PrefetchDecision` 等 C++ 对象中，不使用
JSON，也不要求另一个 pass 读取分析结果。

## 2. 步骤 2：建立 LLVM pass 插件

### 2.1 插件入口

`src/StencilPrefetchPass.cpp` 定义 `StencilPrefetchPass`，它是 LLVM new
pass manager 的 function pass。当前只处理名称以 `stencil_` 开头的非声明
函数，函数名前缀只用于缩小处理范围，不参与 stencil 类型判断。

pass 从 `FunctionAnalysisManager` 获取：

1. `LoopInfo`：寻找循环和最内层循环。
2. `ScalarEvolution`：分析归纳变量、步长、trip count 和地址偏移。
3. `DominatorTree`：检查谓词、地址基址和插入位置的支配关系。
4. `TargetTransformInfo`：为后续目标代价扩展保留接口。
5. `AssumptionCache`：获得函数中的假设信息。

### 2.2 注册方式

插件提供两种注册入口：

- `registerPipelineParsingCallback` 注册显式名称
  `function(stencil-prefetch)`。
- `registerOptimizerEarlyEPCallback` 让 Clang 使用
  `-fpass-plugin` 时自动把 pass 加入优化管线。

两种方式最终运行同一个 `StencilPrefetchPass::run`，不会维护两套实现。

### 2.3 构建方式

`CMakeLists.txt` 使用 LLVM 的 `add_llvm_pass_plugin`，将以下源码编译为
`StencilPrefetchPass.dylib` 或 `StencilPrefetchPass.so`：

```text
src/StencilAnalysis.cpp
src/StencilPrefetchDecision.cpp
src/StencilPrefetchPass.cpp
```

当前插件使用 LLVM 18 的头文件和 ABI。测试输入由 Apple Clang 21 生成，
因此 `build_and_test.sh` 只在临时 IR 中移除 LLVM 18 无法解析的
`captures(none)` 和 GEP `nuw` 文本属性，不改变循环和地址关系。

## 3. 步骤 3：识别 2D5P 和 3D7P

步骤 3 由 `include/StencilAnalysis.h` 和
`src/StencilAnalysis.cpp` 实现。

### 3.1 寻找候选循环

`analyzeStencilFunction` 递归收集函数中的最内层循环，并调用
`analyzeInnerLoop` 检查每个候选。当前识别要求循环满足：

1. 包含 5 个或 7 个 `llvm.masked.load`。
2. 包含一个 `llvm.masked.store`。
3. load 和 store 使用同一个谓词。
4. 谓词由 `llvm.aarch64.sve.whilelo` 生成并支配所有内存访问。
5. `x` 归纳变量是循环 PHI。
6. SCEV 证明归纳步长来自 `llvm.aarch64.sme.cntsw`。
7. 循环中没有普通 store 或非 LLVM 外部调用。

只根据 load 数量不能通过识别；谓词、向量步长和地址关系都必须成立。

### 3.2 合并当前行的逻辑 load

代码使用 `GetPointerBaseWithConstantOffset` 分解 load 地址。若三个 load
相对同一基址的偏移为：

```text
-sizeof(float), 0, +sizeof(float)
```

则把 left、center、right 合并为一条 `current-row` 物理流。
`StreamInfo::Loads` 保存这条物理流对应的三个逻辑 load，后续不会为它们
分别生成重复预取。

### 3.3 识别跨行和跨平面流

去掉最内层 `x` GEP 后，其余流以 current-row 为基准。代码使用 SCEV
判断两条偏移是否互为相反数：

```text
-W, +W
  -> north-row, south-row

-(H * W), +(H * W)
  -> front-plane, back-plane
```

包含至少两个非常量乘法因子的偏移被判定为 plane stride，否则判定为
row stride。最终要求：

| 算子 | 逻辑 load | 物理流 | 地址关系 |
|---|---:|---:|---|
| 2D5P | 5 | 3 | current + 一对 row |
| 3D7P | 7 | 5 | current + 一对 row + 一对 plane |

地址配对不完整时整个候选循环被拒绝，不按函数名或 load 数猜测。

## 4. 步骤 4：生成预取决策

步骤 4 的数据结构和接口位于
`include/StencilPrefetchDecision.h`，算法位于
`src/StencilPrefetchDecision.cpp`。

### 4.1 当前目标 Profile

`getDefaultPrefetchProfile` 返回确定性的 `generic-sme` Profile：

| 参数 | 当前值 |
|---|---:|
| cache line | 64 byte |
| L1 / L2 标称容量 | 64 KiB / 1 MiB |
| L1 / L2 可用比例 | 60% / 60% |
| L1 / L2 预取延迟 | 32 / 96 cycle |
| assumed streaming VL | 64 byte |
| expected row | 4 KiB |
| expected plane/tile | 128 KiB |
| 最大独立流 | 5 |
| 每迭代最大预取指令 | 8 |
| 每迭代最大预取字节 | 512 byte |

当前 kernel 的 `W/H` 是运行时参数，因此第一版使用 Profile 中的代表尺寸
估算复用和容量。该 Profile 是可重复的基线，不代表某个具体 CPU 的最终
PMU 调优结果。

### 4.2 生成候选

`decidePrefetches` 按以下规则生成第一版候选：

```text
2D5P:
  north/south row -> L1

3D7P:
  north/south row -> L1
  front/back plane -> L1 near + L2 far
```

`current-row` 默认关闭，因为连续 `x` 流最可能已经被硬件预取覆盖。
next-row、next-plane 和 next-tile 也尚未启用。

### 4.3 计算距离

每个层级的原始距离为：

```text
raw_distance
  = ceil(prefetch_latency_cycles / useful_cycles_per_iteration)
```

2D 和 3D 分别使用 Profile 中的 8 和 10 个有效 cycle。若 SCEV 能得到
常量 trip count，代码要求循环长度大于两倍原始距离；否则使用 Profile
中的最大距离。距离随后按 cache-line 前沿取整。

当前 Profile 得到：

```text
L1 distance = 4 次向量迭代
L2 distance = 10 次向量迭代
```

### 4.4 选择 KEEP 或 STRM

row 流的复用距离估算为：

```text
2D row: 3 * expected_row_bytes
3D row: 5 * expected_row_bytes
```

plane 流的复用距离使用 `expected_plane_or_tile_bytes`。当复用次数大于
1 且复用距离不超过目标 cache 的有效容量时选择 `KEEP`，否则选择
`STRM`。3D plane 的 L1 near 候选固定使用 `STRM`，避免完整 plane
污染 L1；L2 far 候选在当前 Profile 下使用 `KEEP`。

### 4.5 容量和流量准入

候选按算子优先级排序后依次准入。每接受一个候选都检查：

1. 活跃工作集加预取在途字节不超过目标 cache 的有效容量。
2. 独立物理流数量不超过 `MaxPrefetchStreams`。
3. 每迭代预取指令数不超过上限。
4. 每迭代请求的 cache-line 字节数不超过带宽预算。

L2 near/far 对同一 plane 地址流只计为一条独立物理流，但分别计入预取
指令数和字节数。拒绝原因保存在 `DecisionReason`，并输出到 pass 日志。

当前 Profile 的最终结果为：

| 算子 | 流 | 距离 | 层级 | 策略 | 数量 |
|---|---|---:|---|---|---:|
| 2D5P | north/south | 4 | L1 | KEEP | 2 |
| 3D7P | north/south | 4 | L1 | KEEP | 2 |
| 3D7P | front/back near | 4 | L1 | STRM | 2 |
| 3D7P | front/back far | 10 | L2 | KEEP | 2 |

## 5. 安全构造未来地址并插入

`insertPrefetches` 首先确认每条流的基址支配第一个 stencil load，然后按
不同距离分组。每组只生成一次：

```text
future_x = x + distance * cntsw()
in_range = future_x < interior_end
```

代码使用 `SplitBlockAndInsertIfThen` 创建条件块。只有 `in_range` 为真时
才从物理流基址构造未来地址并调用 `llvm.aarch64.prefetch`。

未来地址使用普通 GEP：

```llvm
%prefetch.addr = getelementptr float, ptr %stream.base, i64 %future_x
```

这里不使用 `inbounds`，避免尾部未来地址越过 C 对象边界时产生 poison。
按距离分组意味着 2D 生成一个 guard，3D 的 L1 和 L2 分别生成一个
guard，而不是为每条流增加一个分支。

intrinsic 参数映射为：

```text
isWrite = 0
target  = L1/L2/L3 对应的 0/1/2
isStream = KEEP/STRM 对应的 0/1
isData = 1
```

插入发生后 pass 返回 `PreservedAnalyses::none()`；没有识别结果或没有
候选时仍返回 `PreservedAnalyses::all()`。

如果函数已经包含 `llvm.aarch64.prefetch`，pass 在获取和修改循环分析
之前报告 `AlreadyPrefetched` 并返回，避免重复运行时再次插入。

## 6. 测试验证了什么

`build_and_test.sh` 构建插件并通过 LLVM 18 Clang 的
`-fpass-plugin` 加载。当前自动检查包括：

1. 2D5P 和 3D7P 分别识别为 3 条和 5 条物理流。
2. 正例恰好产生 8 条决策和 8 个 `llvm.aarch64.prefetch`。
3. 参数组合为 4 条 L1 KEEP、2 条 L1 STRM、2 条 L2 KEEP。
4. current-row 没有软件预取决策。
5. 8 个未来地址都是非 `inbounds` GEP。
6. 2D 使用一个地址 guard，3D 使用两个地址 guard。
7. 名称符合但结构不是 stencil 的 vector-copy 不产生决策。
8. 破坏 2D 的 `±row` 关系后，2D 被拒绝，3D 的 6 条决策仍保留。
9. 8 条 intrinsic 正确降为 4 条 L1 KEEP、2 条 L1 STRM 和 2 条 L2 KEEP。
10. 原始 C 可以通过 `-fpass-plugin` 直接生成带预取汇编。
11. 对已插入 IR 再运行 pass 后仍为 8 条，证明不会重复插入。

生成结果位于：

```text
output/pass_run.log
output/stencil_sme_kernels.after.ll
output/stencil_recognition_report.md
output/stencil_prefetch_decision_report.md
```

## 7. 当前实现边界

当前步骤 2 至步骤 4 已经形成可运行的端到端原型，但仍有以下边界：

1. 只有 `generic-sme` 基线 Profile，尚未按具体 CPU 和 PMU 数据调参。
2. 动态 `W/H` 使用 Profile 代表尺寸，尚未生成运行时 loop versioning。
3. current-row、next-row、next-plane 和 next-tile 默认不插入。
4. L3 候选尚未启用。
5. 当前 assumed VL 等于 cache-line 大小，因此每个候选只生成一个地址；
   多 cache-line VL 的展开仍需后续实现。
